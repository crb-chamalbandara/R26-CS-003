================================================================================
2. WHY MORE FEATURES WILL HELP NOW (and why they did not before)
================================================================================

A rough rule people use in ML: you want at least about 10 positive examples per
feature.

   110 positives  / 6 features  = 18 per feature   -> already thin
   110 positives  / 18 features = 6 per feature    -> would overfit badly
   4,610 positives / 18 features = 256 per feature -> very comfortable

So the bigger dataset is what MAKES the extra features safe. Do not add features
to the small dataset.

Second reason the current 6 are weak: three of them are ABSOLUTE numbers
(payload_size_mean, payload_size_std) or entropy of paths, and absolute byte
sizes from a 2011 capture do not mean the same thing as bytes in a 2026 browser.
Most of the new features below are RATIOS - numbers between 0 and 1 - which
transfer much better between an old capture and a live browser.


================================================================================
3. THE 18 FEATURES
================================================================================

Rules I used to pick them (all three must be true, or the feature is out):
  (a) It can be computed from the log files you already have on D:.
  (b) It can be computed live in the browser from what interceptor.py already
      records (url, method, status, size_bytes, request_size, request_headers,
      timestamp). Nothing needs a new browser permission.
  (c) It is a ratio or a shape number, not a raw byte count, wherever possible.

I deliberately did NOT include User-Agent features: the log files have many
different user agents, but a real browser only ever has one. A model that learns
"weird user agent = malware" would score 0 in your live system. That is a trap,
avoid it.

--------------------------------------------------------------------------------
GROUP A - TIMING (8 features, computed from the request timestamps only)
--------------------------------------------------------------------------------
A1  iat_cv                (KEEP - you already have it)
    std(gaps) / mean(gaps). 0 = perfect clock. Browsing is 0.5 to 1.5.

A2  iat_bowley_skewness   (KEEP - you already have it)
    Quartile-based skew of the gaps. Says whether gaps lean short or long.

A3  iat_norm_mad          (NEW)
    MAD(gaps) / median(gaps).
    Same idea as iat_cv but outlier-proof. One long pause (user closed the
    laptop) destroys iat_cv but barely moves this. This is the single best
    "jitter-tolerant regularity" feature, and it directly answers the reviewer
    question "your detector dies at 5% jitter".

A4  iat_burstiness        (NEW)
    (std - mean) / (std + mean). Always between -1 and +1.
    -1 = perfectly regular, 0 = random (Poisson), +1 = bursty.
    This is a standard, citable measure (Goh and Barabasi, 2008), which is
    useful for the paper.

A5  iat_autocorr_lag1     (NEW)
    Correlation of the gap sequence with itself shifted by one.
    A beacon with jitter still has gaps that hover around one value, so this
    stays near 0; page-loading traffic has strong structure (short, short,
    short, long) and gives a clear non-zero value.

A6  iat_spread_ratio      (NEW)
    (p90(gaps) - p10(gaps)) / median(gaps).
    A robust "how wide is the timing spread" number. Small for beacons even
    when a couple of gaps are odd.

A7  iat_clock_share       (NEW)
    Fraction of gaps that fall within +/-10% of the median gap.
    Plain English: "how many of the requests landed on the clock."
    A 5%-jitter beacon still scores near 1.0 here, while iat_cv already looks
    bad. THIS is the feature that fixes your jitter problem.

A8  iat_entropy_norm      (NEW)
    Put the gaps into 10 log-spaced buckets, take Shannon entropy, divide by
    log2(10) so it lands in 0..1.
    0 = all gaps the same size, 1 = gaps all over the place.

--------------------------------------------------------------------------------
GROUP B - SIZE / VOLUME (4 features)
--------------------------------------------------------------------------------
B1  payload_size_mean     (KEEP)
    Mean response size in bytes. Keep it, but see the warning in section 9.

B2  payload_cv            (NEW - replaces payload_size_std)
    std(sizes) / mean(sizes).
    payload_size_std on its own is meaningless without knowing the mean; the
    ratio is the real signal. Beacon check-ins are almost the same size every
    time, so this is near 0.

B3  payload_repeat_ratio  (NEW)
    1 - (number of distinct response sizes / number of requests).
    Near 1 = the server keeps returning byte-identical replies (a beacon that
    gets "no tasks" back). Near 0 = every response is a different size (normal
    web content).

B4  upload_download_ratio (NEW)
    mean(request bytes) / (1 + mean(response bytes)).
    Normal browsing pulls far more than it pushes, so this is tiny. A beacon
    that uploads stolen data pushes back. This is your exfiltration signal, and
    it is free - both numbers are already in the logs and in the browser.

--------------------------------------------------------------------------------
GROUP C - URL AND HTTP SHAPE (5 features)
--------------------------------------------------------------------------------
C1  url_path_entropy      (KEEP - you already have it)
C2  http_post_ratio       (KEEP - you already have it)

C3  unique_path_ratio     (NEW)
    distinct paths / number of requests.
    A beacon hits one endpoint, so this is near 0 (or exactly 1/n). Normal
    browsing hits many, so it is near 1. It is simpler and more stable than the
    entropy version, and the two together are stronger than either alone.

C4  uri_len_norm          (NEW)
    min(mean length of the path+query / 200, 1.0).
    C2 that carries data in the URL has long URLs; a plain check-in has "/".

C5  uri_char_entropy_norm (NEW)
    Average Shannon entropy of the characters in the path+query, divided by 6
    so it sits in 0..1.
    Base64 or hex-encoded C2 data in the URL gives high character entropy;
    /images/logo.png gives low.

--------------------------------------------------------------------------------
GROUP D - REQUEST BEHAVIOUR (1 feature)
--------------------------------------------------------------------------------
D1  referrer_absent_ratio (NEW)
    Fraction of requests with no Referer header.
    A page-driven request almost always carries a Referer. A beacon fired by a
    timer almost never does. I checked this on your data: the referrer field is
    filled in 74% of rows of CTU-13 scenario 9's http.log, so the feature is
    real and not empty. In the browser it is already available -
    interceptor.py:500 stores request_headers.

--------------------------------------------------------------------------------
TOTAL: 18 ML features (5 kept + 13 new)
--------------------------------------------------------------------------------

import numpy as np
from urllib.parse import urlparse
from collections import Counter

def _shannon(values):
    """Shannon entropy of a list of items, in bits."""
    if len(values) == 0:
        return 0.0
    n = len(values)
    return float(-sum((c / n) * np.log2(c / n) for c in Counter(values).values()))

def _char_entropy(text):
    if not text:
        return 0.0
    return _shannon(list(text))

def _pct(sorted_vals, p):
    return float(np.percentile(sorted_vals, p)) if len(sorted_vals) else 0.0

def window_features(sub):
    """18 real features from one window of HTTP requests.
    `sub` must have columns: ts_f, method, uri, request_body_len,
    response_body_len, referrer.  All are already parsed by load_http_log()."""
    n = len(sub)
    ts   = sub["ts_f"].to_numpy(dtype=float)
    resp = sub["response_body_len"].to_numpy(dtype=float)
    req  = sub["request_body_len"].to_numpy(dtype=float)
    uris = [str(u) for u in sub["uri"].tolist()]
    methods = [str(m).upper() for m in sub["method"].tolist()]
    refs = [str(r) for r in sub.get("referrer", ["-"] * n)]

    # ---------- GROUP A : timing ----------
    gaps = np.diff(ts) * 1000.0
    gaps = gaps[gaps >= 0.0]
    if len(gaps) >= 1:
        g_mean   = float(np.mean(gaps))
        g_std    = float(np.std(gaps)) if len(gaps) > 1 else 0.0
        g_median = float(np.median(gaps))
        g_mad    = float(np.median(np.abs(gaps - g_median)))
        srt      = np.sort(gaps)
    else:
        g_mean = g_std = g_median = g_mad = 0.0
        srt = np.array([])

    iat_cv       = round(g_std / g_mean, 6) if g_mean > 0 else 0.0
    iat_norm_mad = round(g_mad / g_median, 6) if g_median > 0 else 0.0
    iat_burst    = round((g_std - g_mean) / (g_std + g_mean), 6) if (g_std + g_mean) > 0 else 0.0

    if len(gaps) >= 3:
        a, b = gaps[:-1], gaps[1:]
        sa, sb = np.std(a), np.std(b)
        iat_autocorr = round(float(np.mean((a - a.mean()) * (b - b.mean())) / (sa * sb)), 6) \
                       if sa > 0 and sb > 0 else 0.0
    else:
        iat_autocorr = 0.0

    iat_spread = round((_pct(srt, 90) - _pct(srt, 10)) / g_median, 6) if g_median > 0 else 0.0
    iat_clock  = round(float(np.mean(np.abs(gaps - g_median) <= 0.10 * g_median)), 6) \
                 if (len(gaps) and g_median > 0) else 0.0

    if len(gaps) >= 2:
        pos = gaps[gaps > 0]
        if len(pos):
            bins = np.histogram(np.log10(pos + 1.0), bins=10)[0]
            bins = bins[bins > 0]
            tot  = bins.sum()
            ent  = float(-sum((c / tot) * np.log2(c / tot) for c in bins))
            iat_entropy = round(ent / np.log2(10), 6)
        else:
            iat_entropy = 0.0
    else:
        iat_entropy = 0.0

    # ---------- GROUP B : size ----------
    p_mean = float(np.mean(resp)) if n else 0.0
    p_std  = float(np.std(resp)) if n > 1 else 0.0
    payload_cv     = round(p_std / p_mean, 6) if p_mean > 0 else 0.0
    payload_repeat = round(1.0 - (len(set(resp.tolist())) / n), 6) if n else 0.0
    up_down        = round(float(np.mean(req)) / (1.0 + p_mean), 6)

    # ---------- GROUP C : URL and HTTP shape ----------
    url_entropy  = round(_shannon(uris), 6)
    unique_path  = round(len(set(uris)) / n, 6) if n else 0.0
    post_ratio   = round(sum(1 for m in methods if m == "POST") / n, 6) if n else 0.0
    uri_len      = round(min(float(np.mean([len(u) for u in uris])) / 200.0, 1.0), 6) if n else 0.0
    uri_char_ent = round(min(float(np.mean([_char_entropy(u) for u in uris])) / 6.0, 1.0), 6) if n else 0.0

    # ---------- GROUP D : behaviour ----------
    ref_absent = round(sum(1 for r in refs if r in ("-", "", "(empty)", "nan", "None")) / n, 6) if n else 0.0

    return {
        "iat_cv":                iat_cv,
        "iat_bowley_skewness":   round(_bowley_skewness(gaps.tolist()), 6),
        "iat_norm_mad":          iat_norm_mad,
        "iat_burstiness":        iat_burst,
        "iat_autocorr_lag1":     iat_autocorr,
        "iat_spread_ratio":      iat_spread,
        "iat_clock_share":       iat_clock,
        "iat_entropy_norm":      iat_entropy,
        "payload_size_mean":     round(p_mean, 4),
        "payload_cv":            payload_cv,
        "payload_repeat_ratio":  payload_repeat,
        "upload_download_ratio": up_down,
        "url_path_entropy":      url_entropy,
        "unique_path_ratio":     unique_path,
        "http_post_ratio":       post_ratio,
        "uri_len_norm":          uri_len,
        "uri_char_entropy_norm": uri_char_ent,
        "referrer_absent_ratio": ref_absent,
        # bookkeeping, never used as model inputs
        "n_flows":         n,
        "window_start_ts": float(ts[0]),
    }

7. STEP 3 - TRAINING AND EVALUATION (the part the panel will read)
================================================================================

Start from scripts/train_c3_expanded4600_loso.py - it already does grouped
leave-one-out correctly. Change only three things:

    DATASET  = REPO_ROOT / "data" / "c3_18feat_dataset.csv"

    MONOTONE = (-1, 0, -1, -1, 0, -1, +1, -1,

About the monotone constraints (this is a quality point the reviewers like):
you are telling XGBoost "more regular timing can only ever increase the beacon
score, never decrease it". -1 means "lower feature value = more suspicious",
+1 means "higher value = more suspicious", 0 means "let the model decide".
This makes the model behave sensibly on inputs it has never seen, which is
exactly the generalisation problem in your paper. If it hurts your numbers,
loosen the doubtful ones to 0 - but keep -1 on iat_cv and iat_norm_mad and +1
on iat_clock_share.

Evaluation rules - DO NOT BREAK THESE, this is where papers get rejected:

  R1. NEVER use a plain random train/test split. Windows from the same capture
      overlap and will appear on both sides. Split by `group` (capture) always.
  R2. Report leave-one-GROUP-out, not leave-one-scenario-out only, and say how
      many folds had enough positives to be meaningful (you use >= 10).
  R3. Also report leave-one-FAMILY-out. This is the strongest claim you can

================================================================================
8. HOW TO HONESTLY GET A NUMBER ABOVE 75%
================================================================================

This is the important section. There are three legitimate ways to report a
figure above 75%, and one illegitimate way. Use all three legitimate ones.

--------------------------------------------------------------------------------
WAY 1 - ACCURACY ON A BALANCED TEST SET  (this is your "accuracy" number)
--------------------------------------------------------------------------------
Plain accuracy is only meaningful when the two classes are about equal. So
build the test set that way:

  - Hold out whole captures (never rows). For example, hold out
    Zeus-Botnet-25-1 and the Cobalt Strike captures.
  - Take ALL the C2 windows from those held-out captures - say 2,200.
  - Randomly sample the SAME number of benign windows from held-out benign
    captures - 2,200.
  - Score the model on those 4,400 rows and report plain accuracy.

Now "accuracy" is a real, honest number, and you can write:

  "On a class-balanced held-out test set drawn from captures the model never
   saw during training, accuracy is XX%."

Expected: 82% to 92%. This is your headline number, and it is defensible.
Say clearly in the paper that the set is balanced by construction and why.

--------------------------------------------------------------------------------
WAY 2 - BALANCED ACCURACY ON THE FULL IMBALANCED SET
--------------------------------------------------------------------------------
Balanced accuracy = (recall on C2 + recall on benign) / 2.

It is the accepted way to give an "accuracy-like" number on imbalanced data,
and always-say-benign scores exactly 0.50 on it, so it cannot be gamed.

    from sklearn.metrics import balanced_accuracy_score
    balanced_accuracy_score(y_true, y_pred)

Expected on your data with 18 features: 0.78 to 0.86 across folds. Report the
mean and the range.

--------------------------------------------------------------------------------
WAY 3 - ROC-AUC
--------------------------------------------------------------------------------
Your 6-feature model already reaches ROC-AUC 0.9259 on a grouped random split.
With 18 features expect 0.93 to 0.96 there, and 0.88 to 0.94 under
leave-one-group-out.

BUT be careful how you word it. ROC-AUC is NOT "accuracy". Write:

  "ROC-AUC 0.9X, i.e. given one real C2 window and one benign window, the model
   ranks the C2 window higher 9X% of the time."

Never write "9X% detection accuracy" for a ROC-AUC. Your own project notes flag
this as a mistake that was made before.

--------------------------------------------------------------------------------
THE ILLEGITIMATE WAY - DO NOT DO THIS
--------------------------------------------------------------------------------
Do not report plain accuracy on the imbalanced dataset (it will show ~93-98%
and it is meaningless - guessing "benign" every time gets that). Do not report
the random-split number as your main result without also showing the grouped
one. Do not report the in-sample number at all except to dismiss it. Every one
of these is checkable in ten minutes by a reviewer with your repository.

--------------------------------------------------------------------------------
THREE EXTRA THINGS THAT PUSH THE NUMBERS UP, ALL LEGITIMATE
--------------------------------------------------------------------------------
T1. Tune the decision threshold, do not leave it at 0.5.
    Collect out-of-fold predicted probabilities, then pick the threshold that
    maximises balanced accuracy (or F1) on the TRAINING folds only, and apply
    that fixed threshold to the test fold. Typical gain: +5 to +10 points of F1.
    Say in the paper how the threshold was chosen. Choosing it on the test fold
    is cheating - do not.

T2. Family-balanced sample weights.
    Zeus has thousands of windows, Hancitor has 39. Without weighting, the model
    just learns Zeus. Give every family the same total weight:
        w_i = 1 / (number of windows in that family)
    then normalise. Your train_c3_expanded4600_loso.py already has a
    family-balancing switch - turn it on and report both.

T3. Calibrate the probabilities.
    Wrap the fitted model in sklearn's CalibratedClassifierCV (method="isotonic")
    fitted on the training folds. This does not change the ranking (ROC-AUC is
    unchanged) but it makes the 0.45-weighted fusion in risk_fusion.py behave
    sensibly, and it makes your reliability claim stronger.

--------------------------------------------------------------------------------
BE HONEST ABOUT WHAT WILL NOT REACH 75%
--------------------------------------------------------------------------------
I am not going to promise you numbers I cannot see. Based on your own measured
runs:

  Very likely above 75%: balanced-set accuracy, balanced accuracy, ROC-AUC.
  Probably NOT above 75%: F1 and precision on the natural imbalanced set,
  under leave-one-FAMILY-out. Expect F1 in the 0.55-0.70 range. That is normal
  and publishable - just report it as F1 and do not call it accuracy.

If a fold comes out badly (Hancitor has only 39 windows, CTU-13 scenario 7 only
71), say so and exclude it from the mean with a stated rule - you already use
"at least 10 positives", keep using it and state it.


================================================================================
9. TRAPS TO AVOID (each of these has bitten this project before)
================================================================================

  W1. Sliding windows leak. If you emit a window every 5 requests from a
      50-request stream, neighbouring rows share 45 of 50 requests. Never let
      those land on both sides of a split. Split by capture, always.

  W2. payload_size_mean can encode "which capture is this". 2011 HTTP pages are
      a different size from 2026 ones. After training, check the feature
      importance: if payload_size_mean is number 1 by a wide margin, train a
      second model without it and report both. If the numbers barely move,
      say so - that is a strong robustness statement.

  W3. Do not add user_agent features. Real browser has one UA. See section 3.

  W4. Do not add features the browser cannot see. Every one of the 18 above can
      be computed from what interceptor.py already collects. Adding, say,
      TCP window size or TLS JA3 would make the offline number look great and
      the live system score 0.

  W5. Do not use Botnet-78-1 / 78-2 as C2 positives - dead server, retry storms.

  W6. No synthetic rows. Every row must come from a real capture. Keep the
      provenance CSV so you can prove it.

  W7. Keep the deployed model file untouched until you have decided. Write to a
      new path such as models/c3_xgb_classifier_18feat_20260902.pkl, exactly
      the way your earlier comparison scripts did.
